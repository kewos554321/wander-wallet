## Design Specificity Verdict

**LLM 評估：品牌聲音與資料模型是專屬的，工作型 chrome 仍可替換。** 分帳語彙（「誰付這筆」「零頭由 X 吸收」）、匯率 provenance（`≈`、market/custom、歷史匯率）、紙感×深湖綠×襯線金額，換成別的產品會立刻失真。但結算頁的 2×2 pastel 磚（`settle-summary-grid.tsx:42-52`）、分類 8 宮格、3 欄篩選 chip 牆，放進任何記帳 App 都成立。設計 token 只做了一半：顏色／圓角／陰影有 scale，**字級與間距沒有**——v2 出現 22 種字級與 5 種 letter-spacing。

**Deterministic scan：0 findings，但這是低信心訊號。** `detect --json components/v2` 回傳 `[]`、exit 0；canary 證明它確實會遞迴 `.tsx`，但 HTML-only 的字級／對比／間距規則讀不到 Tailwind arbitrary classes。原始碼實際有 **43 處 `text-[8px]`–`text-[10px]`**（例：`payer-picker.tsx:135`、`split-summary.tsx:154`、`filter-panels.tsx:282`）。不能把 0 findings 當成 a11y 通過。

**視覺 overlay：** 本 session 無瀏覽器自動化（也沒有 Playwright/Puppeteer），未注入、無 overlay；以上為原始碼與 token 值量測。

## Overall Impression

這是一個有靈魂、有會計誠信、但「入口」還沒設計好的產品。最強的地方是把分帳的錯講清楚（誰超額、差多少、零頭誰吸收）；最弱的地方是讓第一次用的人知道「這筆錢要分給誰」。Material 3 的角度會說：主要動作只有一個、狀態要看得見、破壞性操作要指認目標——這三件事目前都各缺一角。

## What's Working

1. **分帳錯誤的具名＋具額診斷**：`describeSplitIssue()` 會說「小美的固定金額 $800 超過支出總額 $600」，而不是「分帳金額不符」（`split-guardrails.ts:120-165`）。這是同類產品少見的誠實度。
2. **匯率的不確定性被可視化**：`≈`、market/custom chip、可查歷史日期、失敗有重試（`amount-card.tsx:132-195`、`rate-sheet.tsx:186-263`）。Material 的 state visibility 在這裡延伸到「資料可信度」。
3. **互動合約與共用樣式**：`▼ 展開 / › 進另一層 / 無箭頭 = 立即生效` 寫在 `expense-form-fields.tsx:8-11`，create/edit 表單共用 `trip-form-styles.ts`；`Sheet` 有真正的 focus trap 與焦點歸還（`ui/sheet.tsx:36-75`）。這是有設計系統的證據。

## Priority Issues

### P1｜新支出的預設分攤只有付款人，而且兩排 pills 長得一模一樣
- **What**：`initialState` 把 `pool` 設成 `[paidBy]`（`lib/expense-draft.ts:134-143`）。「誰付這筆」與「誰一起分」用同一個 `memberPillClass`（`payer-picker.tsx:13-17`），只靠 13px 標題區分。
- **Why**：Jordan 記「晚餐 600 我付」時，若沒注意到第二排，這筆就變成自己的個人開銷，朋友一毛都不欠——產品承諾直接失效，而且沒有任何警告。Material 的預設應該對齊最常見意圖，或讓偏離預設這件事被看見。
- **Fix**：預設改成「付款人＋全體旅伴」或提供一顆醒目的「大家平分」chip；`pool` 只有自己時顯示「只有你分這筆」的提示；兩排 pills 用不同容器（付款人是單選、分攤是複選）與不同選中樣式。
- **指令**：`clarify` ＋ `harden`

### P1｜主要 CTA 變灰，但原因可能不在視野內
- **What**：送出條件包含 `blockingError`（`expense-form-platform-view.tsx:130`），但 footer 只顯示 `amountIssue ?? submitError`，刻意排除 split 錯誤（同檔 `:66-72`）；split 錯誤渲染在長表單最底部（`split-panel.tsx:468-473`），使用者可能已捲到上方。描述錯誤要 `descTouched` 才出現（`expense-form-fields.tsx:182-186`）。
- **Why**：disabled 的主要按鈕＋看不到原因＝卡死。這是核心 money loop 的阻斷點，Material 要求錯誤靠近欄位、主要動作的可用性可被解釋。
- **Fix**：footer 永遠顯示第一個阻擋原因（含 split）並可點擊捲到該區塊；或按鈕保持可按，按下時聚焦第一個錯誤。描述欄位改為 on-input 即時提示。
- **指令**：`clarify` ＋ `harden`

### P1｜刪除確認不告訴你「刪的是哪一筆」，而且不能復原
- **What**：`ConfirmDeleteDialog` 只收到通用描述「確定要刪除這筆支出嗎？此操作無法復原。」（`expenses-v2.tsx:160-168`、`expense-form-v2.tsx:335-343`），沒有帶入描述／金額／付款人；成功後直接從陣列移除（`useProjectExpenses.ts:91`），沒有 undo；失敗用 `alert()`（同檔 `:75,95`）。
- **Why**：這是全 app 唯一的資料毀滅點，發生在「錢」上；滑動刪除又提高誤觸機率。Material 的 destructive confirmation 要求辨識目標＋明確後果，目前只有後果。
- **Fix**：對話框顯示「刪除『一蘭拉麵晚餐』· TWD 680 · 我付款 · 3/14」；成功後 5 秒 Snackbar「已刪除 · 復原」；`alert()` 改成 dialog 內 inline error。
- **指令**：`harden`

### P1｜小字對比與觸控目標低於可用門檻
- **What**：`--v2-ink-subtle #B7AE9D` 對白約 **2.20:1**、對紙底約 **2.06:1**；`--v2-check #C9BFAC` 約 **1.82:1**，卻是未選 checkbox 的邊框。`ink-subtle` 被用在 9–11px 的日期、群組標題、說明（`expenses-v2-view.tsx:44`、`expense-card.tsx:64-66`）。尺寸：篩選列約 29px、日曆格約 24px、slider thumb 14px、top bar 返回 34px（`v2-top-bar.tsx:38`）、計算機鍵 42px（`calculator-pad.tsx:142`）。
- **Why**：這是 LINE 內行動優先的產品；Material 的 48dp 與 WCAG 的 4.5:1／3:1 是能不能用的門檻，不是美學偏好。
- **Fix**：小於 14px 的文字改用 `ink-muted`（約 5.5:1）；`ink-subtle` 只留裝飾；控制項最小 44×44、日曆格 40px、slider thumb 24px；未選 checkbox 邊框改 `ink-muted`。
- **指令**：`audit` ＋ `polish`

### P2｜篩選牆是「把 query 參數攤在畫面上」，而且跨幣別比較是錯的
- **What**：搜尋＋6 個維度常駐 3 欄 grid（`expense-filter-bar.tsx:59-118`）；「付款旅伴／旅伴」相鄰且只差兩字；金額區間用原始 `expense.amount` 比較（`useExpenseFilters.ts:203-207`），在 TWD＋JPY 旅程等於拿日圓數字跟台幣 slider 比；`AmountPanel` 以 `$` 顯示（`filter-panels.tsx:170`）。
- **Why**：主畫面永久少約 200px、第一筆支出被推到半屏以下；跨幣別比較會給出看似合理但錯誤的結果。
- **Fix**：主畫面只留搜尋＋一顆「篩選 (n)」，其餘進 bottom sheet 分組（對象／金額／日期／其他）；金額先換算成專案幣別再比較與顯示；標籤改「付款人／分攤對象」；active filters 用可移除 chips。
- **指令**：`layout` ＋ `clarify`

## Minor Observations

1. **結算的終點是贊助卡**：使用者剛看完「我欠誰多少」，頁尾接「請我們喝杯咖啡」（`settle-v2-view.tsx:100`）。Peak-end 被用在推銷，而不是「轉帳完成」；而且整頁沒有「我已轉帳／標記完成」的閉環。
2. **兩顆常駐 FAB**：Material 的 FAB 是單一主要動作；AI 與手動新增同時展開，右下角 120px 被吃掉，也讓「哪個是預設」不清楚。
3. **金額精度被 `Math.round` 吃掉**：`expense-summary-card.tsx:23,41`、`settlement-list.tsx:92`、`balance-card.tsx:25-27`、`settle-calc-dialog.tsx:167`；USD/SGD 旅程會出現畫面與帳面不一致，餘額 0.4 元會被宣告「已結清」。
4. **摘要卡的日期與金額語意不對應**：日期 badge 是整趟旅程（`expenses-v2.tsx:102-105`），金額卻是篩選後總額（`expense-summary-card.tsx:15-20`）。
5. **每張支出卡都印「未填寫地點」**（`expense-card.tsx:116`），是負向噪音；沒有地點時應該安靜。
6. **空狀態不一致**：旅程列表有「建立旅程」CTA（`projects-v2-view.tsx:104-114`），支出列表沒有；篩選空結果也沒有「清除篩選」。
7. **旅程卡沒有狀態**：進行中／已完成只存在於篩選器，卡片上的「N 天」badge 全部同色（`projects-v2-view.tsx:141-145`）；日期也沒有年份。
8. **分享文字固定用 base currency**：切換顯示幣別後，畫面與分享文字不一致（`useSettlement.ts:121-133`）。
9. **18:00 後一律「晚安」**（`lib/trip.ts:34-39`），18:30 看到會有點怪。
10. **`getGreeting`、`JoinMode` 預設順序**：`both` 是最後一個選項（`use-project-form.ts:8-12`），第一眼看到的是未選中的 `create_only`。

## Questions to Consider

- 如果 90% 的支出是「我先付、大家平分」，為什麼預設分攤對象是「只有我」，而不是一顆寫著「大家分」的 chip？
- 把篩選牆拿掉，使用者會少做什麼？如果答案是「什麼都不會少」，那 200px 的常駐成本就沒有正當性。
- 結算頁的終點應該是「我已經轉帳完成」，還是「請我們喝杯咖啡」？如果把贊助卡移到結清之後，轉換率會不會反而更高？
- 如果只能留一顆 FAB，你會留 AI 還是手動？現在兩顆都在回答「怎麼記帳」，卻沒有回答「哪個是預設」。
